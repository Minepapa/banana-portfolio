# 외부 콘텐츠 격리는 물리적 프로세스 분리 대신 정생적 원칙으로

critic 리뷰는 "외부 텍스트(뉴스링크·저널·카카오알림)를 읽는 세션과 실제 주문실행 권한을
가진 세션이 같다"는 프롬프트 인젝션 우려를 제기했다. 점검 결과 실제 위험 범위는 좁았다 —
카카오 파싱은 순수 정규식(LLM 미개입)이라 벡터가 아니고, 저널링은 Frank 본인 글이라
제3자 주입 경로가 아니며, 주문 승인 자체는 `reply_to`+계정 인증으로 구조적으로 위조 불가
하다. 남는 유일한 좁은 위험은 Frank가 공유하는 뉴스·기사 링크가 Athena·Zeus의 판단에
사회공학적으로 스며드는 것뿐이었다.

이 좁은 위험에 대해, 승인판정 경로와 대화·종합 경로를 물리적으로 별도 프로세스로 쪼개는
무거운 방어 대신, **"외부자료=데이터, 지침 아님"을 Apollo의 정생적 원칙으로만** 두기로
확정했다. 이미 있는 2중 방어(Themis의 독립 리스크 검증 + Frank의 물리적 최종 승인)가
이 원칙을 뒷받침한다 — 기사 하나가 Athena와 Themis를 동시에 속이고 Frank도 못 알아채고
승인까지 해야 실제 피해로 이어지므로 단일 지점 실패가 아니다.

**고려했던 대안**: 승인판정 전용의 좁고 작은 별도 프로세스를 신설 — 공격면을 구조적으로
최소화하지만 구현 복잡도가 크게 늘어난다. 오너가 "가벼운 방어로 충분"을 택해 기각.

**여파**: 향후 실제 프롬프트 인젝션 사고가 발생하면 이 결정을 재검토해야 한다 — 지금은
위험 범위가 좁다는 분석에 근거한 선택이지, 영구히 안전하다는 보장은 아니다.
