# banana-portfolio v2 — 구현 계획서

> 이 문서는 `docs/ARCHITECTURE-V2.md`(설계 정본)의 실행 순서를 정리한 것이다. 설계
> 내용 자체는 재정의하지 않는다 — "무엇을 만들지"는 이미 확정됐고, 여기서는 "어떤
> 순서로, 무엇을 재사용해서, 어떤 스킬로" 만들지만 다룬다.
>
> **아직 구현 시작 아님** — `CLAUDE.md`의 "이제 구현해보자" 해제 조건 전까지는 이
> 계획서 자체도 설계 문서 작성의 일부다.

## 순서를 정하는 원칙

1. **위험한 것(실제 돈이 걸린 것)을 최대한 뒤로 미룬다** — 특히 KIS 실제 주문 실행
   API는 섀도우모드가 이미 있으므로 "로그만 남기는 경로"로 대부분의 개발·검증이
   가능하다. 실제 체결 API는 섀도우모드로 충분히 검증된 뒤, 실전전환 직전에 만든다.
2. **모두가 의존하는 기반부터** — Vault 구조·공용 락 유틸이 없으면 그 위의 어떤 것도
   못 만든다.
3. **v1 자산을 최대한 재사용** — 새로 짜는 게 아니라 "이식"인 부분을 각 단계에 명시한다.
4. **각 단계마다 완료 기준(Definition of Done)을 둔다** — "설계에 다 있으니 만들면
   끝"이 아니라, 뭘 확인해야 다음 단계로 넘어가도 되는지 명시한다.

|---|---|---|---|---|

## Phase 0 — 조직 정합화

**왜 먼저**: 비용이 거의 없고, 뒤 단계에서 "Kairos가 뭘 하는 부서인지" 코드가 참조할
문서 자체가 지금 없다(`kairos.md` 부재 확인됨). 먼저 정리해두면 이후 단계에서 매번
설계문서를 재해석할 필요가 없다.

**작업**:
- `.claude/agents/kairos.md` 신설 — 퀀트 트랙 전담(팩터신호 계산·종합·전략수립), 2단
  필터 원칙(Node 계산→의미있을 때만 LLM), 담당 데이터 소스(pykrx·OpenDart) 명시
- `athena.md`에 ISA 배당전략·분기점검·3계좌 합산 노출보고 역할 반영
- `zeus.md`·`PANTHEON.md`에 "투자실행협의체가 트랙별로 분리된 두 체인"이라는 최신
  구조 반영 (ADR 0004 추신 노트와 동일 내용을 헌장에도 반영)

**완료 기준**: 5개 에이전트 파일이 `ARCHITECTURE-V2.md`의 최신 부서 역할표와 1:1로
대조해서 어긋남이 없다.

**추천 스킬**: 별도 스킬 불필요 — 직접 편집. 완료 후 서로 다른 문서(설계서 vs 에이전트
정의) 간 정합성이므로 편집 뒤 `grep`으로 교차 확인.

## Phase 1 — Vault 기반 구조 + 공용 인프라

**왜 이 순서**: 이후 모든 단계(파싱·안전장치·트랙 로직)가 Vault State/Facts 파일을
읽고 쓴다. 이게 없으면 다음 단계 전부가 막힌다.

**작업**:
- Vault 물리 폴더 생성(기존 `profile/playbooks/learning/skills`와 완전 분리된 새
  경로) + Google Drive 동기화 마운트 확인
- 4대 분류 폴더 구조: Facts(Ledger/MarketPolls) · State(Holdings/Allocation/
  Baselines) · Decisions(Evaluations/PositionJournal/Proposals) · Knowledge
  (Profile/Playbook/Reports)
- **`state-writer.mjs`(신규, 공용 유틸)**: State 파일 락파일 기반 동시쓰기 방지 +
  원자적 교체(임시파일 쓰기 후 rename). 이후 모든 State 쓰기 코드가 이 모듈 하나만
  거치도록 강제
- 시크릿 보관 경로 확인(`~/.config/banana-portfolio/`, macOS Keychain) — v1 그대로 계승

**완료 기준**: `state-writer.mjs`에 대해 "두 프로세스가 동시에 같은 State 파일을 쓰면
한쪽이 유실되지 않는다"는 테스트가 통과한다. Vault 폴더가 Mac·안드로이드 양쪽에서
열람 가능하다(Facts/MarketPolls는 안드로이드 동기화 대상에서 제외).

**추천 스킬**:
- **`tdd`(superpowers:test-driven-development)** — 락·원자적쓰기는 동시성 버그가
  전형적으로 숨는 지점이라 테스트 먼저 작성하는 게 특히 이득이 큰 케이스
- **`setup-pre-commit`** — 이 시점에 lint·test·type check pre-commit 훅을 세팅해두면
  이후 모든 Phase가 혜택을 받는다(금융 데이터를 다루는 코드라 커밋 시점 검증 가치가 큼)

## Phase 2 — 카카오 알림 → Vault 파싱 파이프라인 이식

**재사용**: `scripts/jobs/parse-notifications.mjs`의 정규식 파서(NH·삼성·한국투자,
체결/배당/펀드적립/금현물/예수금/환전 6종) — **파싱 로직 자체는 그대로**, 출력 대상만
구글시트에서 Vault Facts/Ledger로 교체. v1 dedup 키(체결=`날짜|구분|종목명|수량` 등)도
Vault frontmatter 고유키 필드로 그대로 이식(새로 설계하지 않음).

**신규**: 이벤트당 파일 하나로 쓰는 Vault 기록 함수(내부적으로 Phase 1의
`state-writer.mjs`와 같은 원자적 쓰기 패턴 적용, 단 Facts는 추가전용이라 락 필요성은
낮음).

**완료 기준**: 구글시트 "알람" 탭 임시중계 → 파싱 → Vault Facts/Ledger 기록까지 실제
샘플 알림으로 end-to-end 확인. 같은 알림을 두 번 넣어도 중복 기록되지 않는다(멱등성).

**추천 스킬**: **`tdd`** — 브로커별 정규식 파서는 이미 v1에 테스트가 있을 가능성이
높으므로, 먼저 기존 테스트를 이식하고 출력 대상 변경분만 새 테스트로 보강.

## Phase 3 — 백업 · 장애감지

**재사용**: `record-heartbeat.mjs` 패턴(v1) 그대로 계승.

**신규**:
- 매일 밤 Vault 폴더를 별도 비공개 git 리포에 스냅샷 커밋하는 launchd 잡
- 독립 워처(30분 주기 launchd) — 상시 텔레그램 세션 프로세스 생존 체크 + 카카오파싱
  하트비트(기대주기 2배 초과 시 경보) — 워처 자신이 텔레그램 `reply`를 직접 호출

**완료 기준**: 상시 세션을 의도적으로 죽여봤을 때 30분 내 텔레그램 경보가 온다. 전날
밤 스냅샷에서 Vault 폴더를 실제로 복구할 수 있다(1회 리허설).

**추천 스킬**: 별도 스킬 불필요 — v1 launchd 패턴 그대로 포팅하는 작업. `tdd`는
하트비트 임계치 판정 로직 정도에만 적용.

**병렬화**: Phase 0·1과 독립이므로 Phase 1 완료 즉시 병렬 착수 가능
(**`superpowers:dispatching-parallel-agents`** 활용 여지).

## Phase 4 — 안전장치 계층 (검문소 · 킬스위치 · 섀도우모드)

> ⚠️ **이 프로젝트에서 가장 신중해야 하는 단계.** critic 리뷰 TIER 1 대응으로 설계된
> 부분이고, 여기 버그가 나면 승인 안 된 주문이 나가거나 반대로 승인된 주문이 막힌다.

**작업**:
- 검문소 6종 판정 로직: 가격이탈(±1%)·보유현황 정합성·중복실행 방지·제안-승인
  일치성·시장개장 상태·단일 활성 제안 원칙·거부 재상정 쿨다운
- 킬스위치("정지"/"STOP" 명령 즉시 반영, 명시적 해제만)
- **섀도우모드**: 이 시점엔 KIS 실주문 API가 아직 없으므로(Phase 11), 브로커 호출
  자리에 "SHADOW: 실제였다면 OO 10주 매수" 로그만 남기는 경로로 구현 — 이게 바로
  Phase 8·9(트랙 로직)가 실제 돈 없이 검증될 수 있게 해주는 핵심 전제
- 지정가(limit order) 우선 원칙은 Phase 11에서 실주문 붙을 때 반영(지금은 설계만)

**완료 기준**: 검문소 6종 각각에 대해 "막아야 하는 상황을 실제로 막는다"는 테스트가
있다. 섀도우 로그가 Decisions/Proposals에 "섀도우체결" 상태로 남고 Facts/Ledger에는
안 섞인다.

**추천 스킬**:
- **`tdd`** — 검문소는 이 프로젝트 전체에서 테스트 커버리지가 가장 중요한 지점
- **`security-review`** — 승인 위조 불가성(reply_to 엄격 매칭), 시크릿 미노출 여부를
  코드 레벨에서 한 번 더 검증
- **`/code-review`**(또는 `oh-my-claudecode:code-reviewer`) — 이 프로젝트 자체 규칙
  (커밋 전 code-reviewer 패스, 저자와 분리)이 특히 이 Phase에 적용돼야 함

## Phase 5 — 텔레그램 승인 흐름

**재사용**: `scripts/lib/telegram.mjs`(기본 발송)는 참고하되, 실제 상시 응답 메커니즘은
Claude Code의 텔레그램 채널 플러그인(`claude --channels plugin:telegram@...`)을 쓴다
— v1의 폴링 봇과 다른 인프라이므로 이 부분은 **재사용이 아니라 신규 배선**.

**작업**:
- `com.banana.*.plist` 패턴으로 상시 세션 감시 launchd job(KeepAlive: true) 등록
- `reply_to` 기반 제안↔답장 매칭(원본 제안 메시지 ID로 식별), 없을 때 폴백 규칙
  확정(가장 최근 미처리 제안으로 간주 여부)
- 부서 라벨(`[투자전략실 Athena]`) + `[Zeus]` 코멘트 메시지 형식
- 부서 직접 호출(예: "카이로스, ~") — 메시지 시작 키워드 매칭으로 단순 구현

**완료 기준**: 실제 텔레그램에서 제안 발송→"승인" 답장→검문소 통과→섀도우 체결까지
전체 왕복이 한 번 이상 성공. 봇 토큰 중복 실행(409 Conflict) 방지 로직 확인.

**추천 스킬**:
- **`telegram:configure`**, **`telegram:access`** — 채널 자체 설정·페어링
- **`tdd`** — `reply_to` 매칭 로직

## Phase 6 — Firestore 미러 + 대시보드 앱

**재사용**: `useGoogleSheets.js`의 구글 OAuth(GSI) 패턴을 Firestore 인증에도 재사용.
기존 탭 컴포넌트(`src/tabs/*`) 상당수를 축소·재배선(신규 개발보다 삭제·정리가 많음).

**작업**:
- Firestore 문서 7종 스키마 구현(`mirror/home`·`holdings`·`allocation`·`dividends`·
  `profits`·`trades`·`latestReport`) — 이미 확정된 필드 그대로
- 앱 탭 정리: 남는 7개(홈·보유종목·자산분배·배당금·수익금·체결내역·리포트) vs 제거
  대상(KPI·노트·과거리포트 탭)
- 대기중 제안 배지(`mirror/home.pendingProposalCount`)
- 데이터 신선도 배너(`updatedAt` 2시간 초과 시)

**완료 기준**: `npm run dev`로 실제 브라우저에서 7개 탭이 Firestore 미러 데이터를
정상 표시. 배지·신선도 배너 동작 확인.

**추천 스킬**:
- **`run`** — 실제 앱을 띄워서 눈으로 확인(이 프로젝트 CLAUDE.md의 "UI 변경은 브라우저
  테스트 필수" 원칙과 정확히 일치)
- **`tdd`** — 이미 `src/lib/*.test.js` 컨벤션이 있으므로 그대로 계승

## Phase 7 — v1 → Vault 데이터 마이그레이션

> ⚠️ **개인 재무 데이터의 조용한 변환 오류가 가장 위험한 지점.** 컷오버 직전, Phase
> 1~6이 전부 실제 데이터로 동작 확인된 뒤에 실행한다(너무 일찍 하면 그 사이 v1에 새로
> 쌓인 데이터를 놓친다).

**작업**:
- `migrate-v1-to-vault.mjs`(1회성 스크립트) — `sheets-common.mjs`의 시트 읽기 유틸 재사용
- 시트 탭 → Vault 매핑표대로 변환(체결/배당/수익금/일별스냅샷 → Facts/Ledger,
  보유종목 → State/Holdings, 평가노트 → Decisions/Evaluations, 포지션저널 →
  Decisions/PositionJournal 등 — "실시간시세"는 변환 안 함)
- **검증**: 변환 후 Vault 기준 계좌별 보유수량·평가액 합계가 v1 시트 값과 정확히
  일치하는지 자동 대조
- v1 launchd 잡 중단, 구글시트는 삭제하지 않고 읽기전용 아카이브로 보존

**완료 기준**: 대조 검증 스크립트가 모든 계좌·자산군에서 0건의 불일치를 보고한다.
불일치가 하나라도 있으면 원인 규명 전까지 컷오버하지 않는다.

**추천 스킬**:
- **`superpowers:using-git-worktrees`** — 마이그레이션 스크립트 개발·리허설을 메인
  작업트리와 분리해서 진행(실수로 실제 컷오버가 조기 실행되는 사고 방지)
- **`tdd`** — 매핑 규칙 하나하나(특히 dedup 키 이식)에 대한 단위 테스트
- **`superpowers:verification-before-completion`** — "합계 일치"를 눈대중이 아니라
  실행 가능한 검증 스크립트 출력으로 확인 후에만 완료 선언

가능.

**추천 스킬**: **`tdd`**(팩터 계산·순위 로직), **`/code-review`**.

**병렬화**: Phase 8과 서로 독립(다른 부서·다른 계좌) — 동시 진행 가능.

## Phase 10 — 백테스트 자체평가 시스템

> Phase 9의 퀀트 알고리즘이 실전 투입 자격이 있는지를 검증하는 **게이트**다. 이 단계를
> 통과하지 못하면 Phase 11(실주문)로 넘어가지 않는다.

**작업**:
- 워크포워드 분석(5년 in-sample→1년 out-of-sample, 윈도우 이동)
- Node 성적표 계산(연평균수익률·샤프비율·MDD·벤치마크 초과수익)
- **Deflated Sharpe Ratio**(Bailey & López de Prado 2014 — 다중검정 보정, 시도한
  파라미터 조합 수 자체 기록)
- 통과판정(벤치마크 대비 상대비교, 절대숫자 금지) → 통과 시 섀도우모드 병행, 실패 시
  Zeus 보고 후 파라미터 재검토
- OCF/P 단일 vs MSCI 3지표 조합 vs OCF/P+PEAD 필터 비교(오늘 세션에서 보류해둔 후보들)

**완료 기준**: 과거 데이터로 최소 1회 전체 워크포워드 사이클을 완주하고 DSR 유의성
판정까지 나온다.

**추천 스킬**:
- **`research`**(skill) — DSR·워크포워드 공식을 구현 전에 원 논문 대조로 재확인(이번
  세션에서 PEAD·Han·Lee·Kang 논문을 WebSearch로 검증했던 것과 같은 패턴)
- **`oh-my-claudecode:scientist`**(agent) — 통계 방법론 검증에 특화, 코드 구현 전
  방법론 자체의 정확성 리뷰에 적합
- **`tdd`** — DSR·샤프비율 계산 자체는 순수 함수라 테스트 적합도가 매우 높음

## Phase 11 — 브로커 실주문 API (KIS 매수/매도)

> ⚠️ **실제 자금이 처음 걸리는 지점.** 지금 `scripts/lib/kis.mjs`는 시세·잔고조회
> 전용이고 "자동매매는 이 모듈의 범위 밖"이라고 코드 주석에 명시돼 있다 — 주문 실행은
> 완전히 새로 만드는 부분이다.

**작업**:
- KIS 주문 API 연동(매수/매도), 지정가 우선 원칙 반영
- Phase 4 검문소의 "SHADOW: 로그만" 경로를 실제 API 호출로 교체(섀도우/실전 스위치는
  유지)
- 레이트리밋 처리(v1 자산 승계 — HTTP 500으로도 오는 레이트리밋을 놓쳤던 v1의 근본
  버그가 이미 수정된 이력 있음, 그 교훈 재적용)

**완료 기준**: 섀도우모드에서 Phase 8·9가 **둘 다** 최소 1개월 이상 안정적으로
운영됐고, Phase 10 백테스트 게이트를 통과한 뒤에만 이 Phase 착수. 소액 실거래로
3~6개월 병행 검증 계획(설계서에 이미 명시)과 맞물림.

**추천 스킬**:
- **`security-review`** — 이 Phase는 필수. 시크릿 노출·주문 위조·레이트리밋 우회 등
  전부 재점검
- **`git-guardrails-claude-code`** — 실거래 코드가 들어간 시점부터 위험한 git 조작을
  훅으로 막아두는 것을 권장
- **`tdd`** + **`/code-review`**(엄격 적용)
